Dachshund60F – Testing the Limits of AI on a Full Keyboard Build

A tri-mode (USB, Bluetooth LE, 2.4 GHz) 60% keyboard designed from scratch: three PCBs, a switch plate, a CNC case, custom firmware, a config protocol, a driver library and a desktop configurator. I built it with Claude Code doing much of the legwork, to find out where AI is strong, where it fails, and where I still add the value.

// STATUS: PRE-PCB ORDER

All three boards are designed and the firmware is built and tested on a PC and in CI. No PCBs have been ordered yet, so nothing has run on real hardware. The project is still in development and testing.

Design → Engineering: the AI's checks all passed, but it still picked an encoder that turned the wrong way and a push switch nobody could reach. Reviewing the design as an object someone will hold is what caught both.

ASSEMBLING KEYBOARD...

01 // WHY THIS PROJECT EXISTS

AI is moving into the problem space engineers and developers have worked in for decades. I wanted to stop guessing about what that means and test it on a real product. The Dachshund60F is that test: a combined hardware and software build big enough to push AI past the easy parts.

The rules were simple. Claude Code drafts, routes, writes and tests. I set the direction, choose between options and review everything. The repository is a public record of who decided what, so I can see exactly where the AI held up, where I had to step in, and what value I bring that it doesn't.

// BOARD SPECIFICATIONS

  • MCU: nRF52840 (Raytac MDBT50Q-P1MV2 pre-certified module)
  • Layout: 60% with F-row, 80 switch positions, hot-swap, screw-in stabilisers
  • Connectivity: USB, Bluetooth LE and a 2.4 GHz dongle (second nRF52840)
  • Mount: FR4 plate on eight silicone gasket socks in a CNC aluminium case
  • Input: Bourns PEC12R roller encoder with push switch, used like a mouse wheel
  • Power: 1S LiPo, MCP73831 charger with a load-sharing power path
  • Display: Header for an OLED or 2.13" e-paper status screen

02 // WHO DID WHAT

The split held for the whole project: the AI did the volume, I owned the judgement.

What the AI Did

  • PCB Grind Schematic entry, routing passes, footprint checks, DRC/ERC runs and STEP exports across four KiCad projects.
  • Firmware & Tests Zephyr firmware over 15 phases, a hardware-free keymap engine with host unit tests, and a fuzzed protocol parser.
  • Software Stack Protocol code generator, TypeScript host library, and the Doghouse configurator app with desktop packaging.
  • Case CAD & Docs A parametric CadQuery case, the renders on this page, CI, a bring-up test plan and a detailed progress log.

What I Did

  • Scope & Architecture Chose the MCU, tri-mode wired-first build order, own firmware over a QMK/ZMK fork, and a driverless HID design.
  • Engineering Trade-offs Picked between options where each answer was reasonable: power path, LED logic levels, polling rate, encoder part.
  • Physical Review Checked how parts actually move, fit and feel, which is where the AI's biggest mistakes were (see 04).
  • Industrial Design Set the case form, materials, gasket mount, thumb scoop and the wheel's look and feel.

03 // DECISIONS I MADE

A selection from the decision log in the repository. Each one came up as a question with more than one reasonable answer, and the call was mine.

Decision What I Chose Why
Microcontroller nRF52840 on the keyboard and the dongle RP2040 and STM32 have no Bluetooth. One chip family at both ends keeps one toolchain.
Build Order Tri-mode, but wired first Wireless doubles the firmware. A solid USB base keeps radio bugs separate from keymap bugs.
Driver No kernel driver: a vendor HID interface plus a user-space library Kernel drivers need signing on Windows and entitlements on macOS. This works anywhere with nothing to install.
Power Path Load-sharing circuit (P-MOSFET + Schottky) on the charger Without it the board only ran from the battery. Now it runs from USB with the switch off or no cell fitted.
LED Data Line SN74LV1T34 level-shifting buffer On USB the LEDs see ~4.7 V, so a 3.3 V data line has no margin. A proper buffer beat a diode drop or hoping.
Polling Rate Stay at 1 kHz on the nRF52840 and cut latency in firmware Going higher meant a new module, bootloader and board. The biggest delays I control are debounce and tap-hold anyway.
Mounting No PCB mounting holes; gasket-mounted FR4 plate A softer, more even typing feel and a simpler board. I own the case and mounting design.

04 // WHERE THE AI GOT IT WRONG

The AI's work passed its own checks: DRC was clean and the tests were green. The serious problems were physical ones, about how a part moves under a finger. I found them by reviewing the design as an object someone will use, which is exactly what my industrial design training taught me to do.

Catch 01: Wrong Encoder Orientation

The roller needs an encoder whose shaft runs parallel to the board, so it turns like a mouse wheel. The AI put the PEC12R-4220F in the BOM: Bourns' axial part, whose shaft points straight up like a volume knob. Its own cross-check had the two part families backwards. The footprint was right, so nothing automated flagged it. I caught the mismatch and moved it to the radial PEC12R-2230F with a 30 mm shaft.

Catch 02: A Button You Couldn't Press

The AI also had the push-button wrong. It treated the click as a press down on the wheel, but on this encoder the switch is pressed along the shaft (0.5 mm of travel), and the end of the wheel was buried inside the case wall. In the model the button looked fine, but nobody could have used it. I had the wheel brought out through a notch in the end wall so a finger can push its end in, and gave it an amber push cap.

Catch 03: Gasket Visual Issues

The gasket socks and their pockets in the case are generated from parameters, and the result still has visual issues. This is one I've decided to resolve myself rather than hand back to the AI: how a gasket sits and reads in a finished case is a design-judgement problem, not a code problem.

05 // THE SOFTWARE SIDE

Firmware, Protocol & Driver

The firmware is custom, on Zephyr / nRF Connect SDK, rather than a fork of QMK or ZMK. The keymap logic is plain C with no hardware in it, so it runs as unit tests on a PC. One YAML file defines the config protocol, and both the C and TypeScript sides are generated from it.

  • USB: NKRO with boot-protocol fallback, media keys, suspend and remote wakeup.
  • Advanced keys: tap-hold, combos, tap dance, macros, Caps Word, Auto Shift, Leader, mouse keys.
  • Wireless: BLE HID with multiple hosts, and a 1 kHz 2.4 GHz link through the dongle.
  • Safety: every host index and length is checked, and the parser is fuzzed. A config channel that writes macros can make a keyboard type commands.
  • Process: one PR per phase, CI on every change, versioned and CRC-checked settings in flash.

Doghouse Configurator

Keymap editing, advanced keys, macros, settings and firmware updates, in the browser over WebHID or as a self-updating desktop app for Windows, macOS and Linux. The boards are named after dogs, so the app is where they live.

06 // STATUS & WHAT I'VE LEARNT

Where It Stands

  • Done in Software All 15 firmware and app phases are built and tested on a PC and in CI.
  • Not Yet Ordered No PCBs have been made. The roller encoder has a long lead time and needs ordering early.
  • Next Fix the gasket visuals, order boards, then run the bring-up plan: rails, current in every state, scan rate, latency and radio range.

The Value I Bring

  • AI Is Fast at the Grind Routing, boilerplate, tests and documentation came quickly and at a volume I couldn't match alone.
  • Engineering Across Disciplines Directing PCB, firmware, software and enclosure work together takes a systems view, and that matters more as AI takes on the individual parts.
  • Decisions Still Need a Person Trade-offs with several valid answers only got settled when I weighed them against what the product is for.
  • Physical Intuition Is the Gap The AI's worst mistakes were about how things move and feel. Clean checks didn't catch them. My industrial design background and shipped-product experience did.
